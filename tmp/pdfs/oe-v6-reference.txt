API-01 | Permissions and common rules
As an authorized user, I can work only with records and actions allowed for my module and company.
1. Read-only users can list/open records but cannot create, edit, submit, return to Draft, delete or record payments.
2. Use existing module permissions. Create permits a new Draft; Update permits Draft changes and authorized status
actions; Delete permits only eligible Draft deletion. Require the payment action permission for recording money and the
Logistics authorization for submitting a Shipper.
3. Enforce permissions server-side for every call. Customer records are deactivated rather than deleted. Payment
records support Create and Read only.
4. Return clear field errors and preserve all data on validation failure. Never save half a document, half a status change
or half a balance change.
Document states and actions - all four types
Current state
Available action / result
New, unsaved
Save as Draft creates a numbered Draft. Direct submission of an unsaved form is not offered.
Saved Draft
Save Changes; Save as Submitted validates all required fields and makes it Submitted.
Submitted
Read-only business fields. Move to Draft only if no downstream document uses it as source, including a
downstream Draft.
Submitted Invoice
Also block Move to Draft if any payment is recorded. No editable payment-status field.
Eligible Draft
Delete may be offered in All Documents only; never inside create, edit or view forms. Reject if referenced
downstream.
Apply complete business validation on Draft save as well as submission in this first release. Document numbers are
unique, system-generated, read-only, at most 20 characters and never reused. Dates use YYYY-MM-DD. Free text is
trimmed before required/length checks. Validate decimal precision and capacity without silently truncating.
Return-to-Draft, source assignment, source release and payment updates must be safe against concurrent requests.
Source-linked drafts keep inherited business values read-only. A returned Draft may be edited only in fields not
inherited from a source.

API-02 | Acceptance and errors
Customer metadata is delivered before the document flow.
1. Create, list, open and update a Customer. Search the list by Customer ID / Customer Name; filter Active / Inactive.
2. Reject a duplicate Customer ID. Changing Customer ID after creation is rejected.
3. Inactive Customers are hidden from new selections. Keep historical Customer references and allow payments
against already submitted invoices even if the Customer later becomes inactive.
4. Customer balance is derived from submitted invoices and actual recorded payments. Users cannot type or overwrite
it. No opening balances, credits or refunds are added in this release.

API-03 to 06 | Line-entry behavior
Shared acceptance criteria for the lines within Sales Quote, Sales Order, Shipper and Sales Invoice APIs.
As an OE user, I can add, read, update and remove item lines on an editable standalone Draft, so that the document
contains the correct items, quantities and prices. These requirements are part of API-03 through API-06, not a separate
Inventory feature.
Simple API contract
Handle lines within the parent document create/read/update calls. A separate line endpoint is not required for this
release. The write request includes the complete intended line collection; the response returns saved lines, stable
system line identifiers, display line numbers, calculated Line Amounts and Document Total. URL and storage design
remain with the team.
Operation
Required behavior
Create Draft with lines
Accept Customer, Warehouse and header fields with at least one valid item line. Generate document and
line identifiers. Save headers and all lines together or save nothing.
Read document
Return all lines in display order with identifier, line number, Item, Description, Quantity, Unit Price, inherited
Warehouse and calculated Line Amount. Return Document Total.
Add a line
On an editable standalone Draft, include a new line without a saved line identifier. Assign its identifier on
save; validate and recalculate amounts.
Update a line
Include the existing line identifier with changed values. It must belong to this document. Revalidate changed
Item, Description, Quantity and Unit Price.
Remove a line
Omit that saved line identifier from the complete submitted collection. Remove it only when the document is
an editable standalone Draft. At least one valid line must remain.
Recalculate
After each successful write, calculate each Line Amount = Quantity x Unit Price, rounded half up to 2
decimals. Total = sum of rounded line amounts. Return the saved values.
Acceptance criteria
1. Blank Source permits manual line entry. Source-selected documents copy all source lines and keep them read-only;
do not allow line additions, changes or removals while the source link is retained.
2. Submitted documents reject all line modifications. They must first pass the existing Move to Draft rules; a retained
source link still locks inherited lines.
3. Line removal changes an item row only; it is separate from deleting a document. No document Delete action appears
inside a form.
4. Save or Submit validates all lines on the server, including when UI checks are bypassed. Do not change totals,
source reservations, status or Customer balance if any line fails.

API-03 - Sales Quote acceptance
1. Create as Draft; read/list, save changes and submit to Submitted. Quote has no Source field.
2. Create a Sales Order from an eligible Submitted Quote or leave Source blank for a standalone Order.
3. Return a Submitted Quote to Draft only if no Order uses it, including Draft Orders. Delete an unreferenced Draft only
from list action.
API-04 - Sales Order acceptance
1. Create as Draft with optional Source Sales Quote Number. Copied fields are read-only; standalone fields are
editable.
2. Submission changes only document status to Submitted. It makes the Order eligible for a Shipper; there is no
Pending or Shipped document status.
3. Block Move to Draft if any Shipper uses the Order. A downstream Draft counts as usage.

API-05 - Shipper acceptance
1. Create standalone or select a Submitted Sales Order. Save Draft; authorized dispatch action is labeled Save as
Submitted.
2. Submitted means dispatch has been confirmed. Do not create a Shipped document status or require a source Order.
3. Carrier is required before Shipper submission: Enter Carrier before submitting the Shipper. Do not implement
Inventory stock changes here. Coordinate dispatch authorization with Logistics. A linked Order remains Submitted.
4. Block Move to Draft when any Invoice uses the Shipper as source, including a Draft Invoice.
API-06 - Sales Invoice acceptance
1. Create standalone or select a Submitted Shipper. Draft has no populated payment status and no payment entry.
2. Require Invoice Total greater than 0 before submission. Submit once: add Invoice Total once to Customer balance
and set payment status Unpaid. Reject zero or negative totals with Invoice Total must be greater than 0.
3. Allow Move to Draft only if no downstream reference and no payment exists. Remove its unpaid balance contribution
once and clear payment status in the same operation. Resubmission adds the total once again.
4. Record-payment action leaves document status Submitted; paid is a payment status only.
