# Sales and Order Entry Database Design

Draft for approval. Updated 20 November 2026 following database-design review. Every Sales table has `RECORD#` and `CNY#` with composite primary key `(CNY#, RECORD#)`. Foreign keys include company scope, single-character flags use `CHAR(1)`, and Customer balance is a stored, server-maintained summary.

## Overview

| Table | Purpose |
| --- | --- |
| `ME_OE_CUSTOMERS` | Customer details and company ownership |
| `ME_OE_DOCUMENTS` | Shared headers for Quotes, Orders, Shippers and Invoices |
| `ME_OE_DOCUMENT_LINES` | Items, descriptions, quantities and prices for each document |
| `ME_OE_SOURCE_LINKS` | The selected source document for a downstream document |
| `ME_OE_PAYMENTS` | Payments received against Invoices |

Existing `ME_COMPANY`, `ME_USERS`, `ME_ACTIONS` and `ME_AUDIT` are reused. Inventory continues to own Items and Warehouses. Logistics owns Trip assignment, dispatch and closure and drives the Shipper transitions described below. These workflow updates follow OE API requirements v7.1, particularly pages 8, 10 and 14-16.

## Identifier naming

| Database name | Meaning | Example |
| --- | --- | --- |
| `RECORD#` | Generated record identifier with up to 15 digits, interpreted together with company | Customer record `1`, document record `10` |
| `CNY#` | Owning company on every Sales table | `1` |
| `CUSTOMER_CODE` | Entered business code, unique within company | `CUST-001` |
| `CUSTOMER_RECORD#` | Reference to Customer `(CNY#, RECORD#)` | `1` |
| `DOCUMENT_RECORD#` | Reference to the line's parent document | `10` |
| `SOURCE_LINE_RECORD#` | Optional immediate predecessor line | `101` |
| `SOURCE_DOCUMENT_RECORD#`, `TARGET_DOCUMENT_RECORD#` | Source and downstream document references | `10` and `20` |
| `INVOICE_RECORD#` | Payment's Invoice reference | `30` |
| `DOCUMENT_NUMBER`, `PAYMENT_NUMBER` | Generated business identifiers | `SO-001`, `PAY-001` |

The primary key on all five Sales tables is `(CNY#, RECORD#)`. The source-link table now also has its own generated `RECORD#`; separate unique rules preserve one target per source and one source per target.

Public API names need not contain `#`: API `id` maps to Sales `RECORD#`, and authenticated company context maps to `CNY#`. Existing Customer URLs such as `/api/v1/sales/customers/1` remain usable. Document URLs continue to use their business numbers. These are database naming changes, not a request to rename Inventory or Logistics JSON fields.

Shared tables are owned by Foundation and are not renamed here. Sales `CNY#` references the current `ME_COMPANY.ID`. Payment `(CNY#, ACTION_REFERENCE)` references the current `ME_ACTIONS(COMPANY_ID, ACTION_REFERENCE)`. If Foundation adopts new names later, update those external references against its approved schema.

`WAREHOUSE_ID` remains an external Inventory identifier and `ITEM_CODE` remains a business code. Their real parent tables and physical key types need confirmation before adding Inventory foreign keys.

## 1. ME_OE_CUSTOMERS

Stores the Customer master record. `RECORD#` is generated automatically for URLs such as `/sales/customers/1`. `CUSTOMER_CODE` is the entered business identifier, such as `CUST-001`.

```sql
CREATE TABLE ME_OE_CUSTOMERS (
    RECORD#                  NUMBER(15) GENERATED BY DEFAULT AS IDENTITY,
    CNY#                     NUMBER(10) NOT NULL,
    CUSTOMER_CODE            VARCHAR2(20 CHAR) NOT NULL,
    CUSTOMER_NAME            VARCHAR2(100 CHAR) NOT NULL,
    IS_ACTIVE                CHAR(1) DEFAULT 'T' NOT NULL,
    CONTACT_NAME             VARCHAR2(100 CHAR),
    EMAIL_ADDRESS            VARCHAR2(254 CHAR),
    PHONE_NUMBER             VARCHAR2(25 CHAR),
    BILLING_ADDRESS_LINE_1   VARCHAR2(150 CHAR) NOT NULL,
    BILLING_ADDRESS_LINE_2   VARCHAR2(150 CHAR),
    CITY                     VARCHAR2(80 CHAR) NOT NULL,
    STATE_PROVINCE           VARCHAR2(80 CHAR),
    POSTAL_CODE              VARCHAR2(20 CHAR),
    COUNTRY                  VARCHAR2(80 CHAR) NOT NULL,
    PAYMENT_TERMS            VARCHAR2(20 CHAR) DEFAULT 'NET_30' NOT NULL,
    AMOUNT_CUSTOMER_OWES_US   NUMBER(18,2) DEFAULT 0 NOT NULL,
    NOTES                    VARCHAR2(500 CHAR),
    WHENCREATED              TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    WHENMODIFIED             TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT ME_OE_CUST_PK PRIMARY KEY (CNY#, RECORD#),
    CONSTRAINT ME_OE_CUST_COMPANY_FK FOREIGN KEY (CNY#)
        REFERENCES ME_COMPANY (ID),
    CONSTRAINT ME_OE_CUST_CODE_UK UNIQUE (CNY#, CUSTOMER_CODE),
    CONSTRAINT ME_OE_CUST_ACTIVE_CK CHECK (IS_ACTIVE IN ('T', 'F')),
    CONSTRAINT ME_OE_CUSTOMERS_TERMS_CK CHECK (
        PAYMENT_TERMS IN ('DUE_ON_RECEIPT', 'NET_15', 'NET_30')
    ),
    CONSTRAINT ME_OE_CUST_BALANCE_CK CHECK (AMOUNT_CUSTOMER_OWES_US >= 0)
);
```

- `CNY#` identifies the owning company through `ME_COMPANY.ID`.
- `CUSTOMER_CODE` remains company-unique and immutable after creation. It is separate from generated `RECORD#`.
- `IS_ACTIVE` uses `T` (true / active) or `F` (false / inactive), initially `T`. Deactivate instead of deleting Customers.
- `PAYMENT_TERMS` uses `DUE_ON_RECEIPT`, `NET_15` or `NET_30`, initially `NET_30`.
- Country is free text. Postal Code remains text so leading zeros are preserved.
- `AMOUNT_CUSTOMER_OWES_US` is stored as `NUMBER(18,2)`, starts at `0.00` and maps to read-only API field `amount_customer_owes_us`, formatted as a two-decimal string. Invoice/payment services maintain it from Submitted Invoices and recorded payments; users cannot enter opening balances, credits, refunds or manual overrides.

## 2. ME_OE_DOCUMENTS

One shared table stores the four document types. `(CNY#, CUSTOMER_RECORD#)` references Customer `(CNY#, RECORD#)`; join it for Customer Code and name. Company is stored directly as `CNY#`, and the composite foreign key prevents linking a document to a Customer in another company.

```sql
CREATE TABLE ME_OE_DOCUMENTS (
    RECORD#                  NUMBER(15) GENERATED BY DEFAULT AS IDENTITY,
    CNY#                     NUMBER(10) NOT NULL,
    DOCUMENT_TYPE            VARCHAR2(20 CHAR),
    DOCUMENT_NUMBER          VARCHAR2(20 CHAR),
    CUSTOMER_RECORD#         NUMBER(15) NOT NULL,
    WAREHOUSE_ID             VARCHAR2(20 CHAR),
    DOCUMENT_DATE            DATE,
    STATUS                   VARCHAR2(20 CHAR),
    VALID_UNTIL              DATE,
    REQUESTED_DELIVERY_DATE  DATE,
    CUSTOMER_PO_NUMBER       VARCHAR2(30 CHAR),
    SHIPPING_ADDRESS         VARCHAR2(500 CHAR),
    PAYMENT_TERMS            VARCHAR2(20 CHAR),
    CARRIER                  VARCHAR2(100 CHAR),
    TRACKING_NUMBER          VARCHAR2(50 CHAR),
    DUE_DATE                 DATE,
    NOTES                    VARCHAR2(500 CHAR),
    WHENCREATED              TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    WHENMODIFIED             TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT ME_OE_DOC_PK PRIMARY KEY (CNY#, RECORD#),
    CONSTRAINT ME_OE_DOC_COMPANY_FK FOREIGN KEY (CNY#)
        REFERENCES ME_COMPANY (ID),
    CONSTRAINT ME_OE_DOC_CUSTOMER_FK FOREIGN KEY (CNY#, CUSTOMER_RECORD#)
        REFERENCES ME_OE_CUSTOMERS (CNY#, RECORD#),
    CONSTRAINT ME_OE_DOC_NUMBER_UK UNIQUE (CNY#, DOCUMENT_TYPE, DOCUMENT_NUMBER)
);

CREATE INDEX ME_OE_DOC_CUSTOMER_IX
    ON ME_OE_DOCUMENTS (CNY#, CUSTOMER_RECORD#);
```

`RECORD#` is an internal generated number. `DOCUMENT_NUMBER` is the generated business number used in URLs. Numbers are never reused after deletion. `STATUS` uses the states below; the API presents them as `Draft`, `Submitted`, `In Progress` and `Closed`.

| Document type | Allowed states |
| --- | --- |
| Quote, Order, Invoice | `DRAFT`, `SUBMITTED` |
| Shipper | `DRAFT`, `SUBMITTED`, `IN_PROGRESS`, `CLOSED` |

### Shipper lifecycle

| Trigger | Previous state | Resulting Shipper state | Authorized actor |
| --- | --- | --- | --- |
| Save a new Shipper | Unsaved | `DRAFT` | Authorized OE user |
| Submit a valid saved Shipper | `DRAFT` | `SUBMITTED` | Authorized OE user |
| Assign the Shipper to a Trip | `SUBMITTED` | `SUBMITTED` | Logistics |
| Dispatch the linked Trip | `SUBMITTED` | `IN_PROGRESS` | Authorized Logistics integration |
| Close the linked Trip | `IN_PROGRESS` | `CLOSED` | Authorized Logistics integration |

Submitted means ready for Logistics pickup; it does not mean dispatch has occurred. Carrier is required before submission. Only the authorized Logistics integration can apply `IN_PROGRESS` or `CLOSED`; ordinary OE users cannot set these values or directly edit document status.

These rules apply to standalone and Order-linked Shippers. A linked Sales Order remains Submitted. No In Transit or Delivered document states are added to Orders.

### Document fields by type

| Document type | Date mapping | Applicable additional fields | Example URL |
| --- | --- | --- | --- |
| `SALES_QUOTE` | `DOCUMENT_DATE` = Quote Date | Valid Until, Requested Delivery Date, Shipping Address, Payment Terms | `/sales/quotes/SQ-001` |
| `SALES_ORDER` | `DOCUMENT_DATE` = Order Date | Requested Delivery Date, Customer PO Number, Shipping Address, Payment Terms | `/sales/orders/SO-001` |
| `SHIPPER` | `DOCUMENT_DATE` = Shipment Date | Shipping Address, Carrier, Tracking Number | `/sales/shippers/SH-001` |
| `SALES_INVOICE` | `DOCUMENT_DATE` = Invoice Date | Payment Terms, Due Date | `/sales/invoices/INV-001` |

Customer, Warehouse and Notes apply to every document type. Fields not applicable to a document type remain empty. Carrier may be empty in a Draft Shipper and is needed on submission.

Shipping Address and Payment Terms are saved document values: initially defaulted from Customer or copied from the source where applicable. They must not change when the Customer master is edited. Invoice terms can be edited on a Draft, including a linked Invoice.

Due Date is stored because the caller may override the date calculated from Invoice Date and Payment Terms. It cannot always be reconstructed from those two fields.

## 3. ME_OE_DOCUMENT_LINES

Stores the complete ordered item collection for each document. Each saved line has its own generated `RECORD#`.

```sql
CREATE TABLE ME_OE_DOCUMENT_LINES (
    RECORD#              NUMBER(15) GENERATED BY DEFAULT AS IDENTITY,
    CNY#                 NUMBER(10) NOT NULL,
    DOCUMENT_RECORD#     NUMBER(15) NOT NULL,
    LINE_NUMBER          NUMBER(10) NOT NULL,
    ITEM_CODE            VARCHAR2(30 CHAR),
    DESCRIPTION          VARCHAR2(200 CHAR),
    QUANTITY             NUMBER(12,3),
    UNIT_PRICE           NUMBER(12,2),
    SOURCE_LINE_RECORD#  NUMBER(15),
    WHENCREATED              TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    WHENMODIFIED             TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT ME_OE_LINE_PK PRIMARY KEY (CNY#, RECORD#),
    CONSTRAINT ME_OE_LINE_COMPANY_FK FOREIGN KEY (CNY#)
        REFERENCES ME_COMPANY (ID),
    CONSTRAINT ME_OE_LINE_DOCUMENT_FK FOREIGN KEY (CNY#, DOCUMENT_RECORD#)
        REFERENCES ME_OE_DOCUMENTS (CNY#, RECORD#),
    CONSTRAINT ME_OE_LINE_SOURCE_FK FOREIGN KEY (CNY#, SOURCE_LINE_RECORD#)
        REFERENCES ME_OE_DOCUMENT_LINES (CNY#, RECORD#),
    CONSTRAINT ME_OE_LINE_POSITION_UK UNIQUE (CNY#, DOCUMENT_RECORD#, LINE_NUMBER)
);

CREATE INDEX ME_OE_LINE_SOURCE_IX
    ON ME_OE_DOCUMENT_LINES (CNY#, SOURCE_LINE_RECORD#);
```

- `(CNY#, DOCUMENT_RECORD#)` identifies the parent document in `ME_OE_DOCUMENTS(CNY#, RECORD#)`.
- `LINE_NUMBER` records display order. Repeated Items are allowed on separate lines.
- `ITEM_CODE` is the Inventory selection code accepted by the current API. Item details are obtained from Inventory instead of duplicated here.
- `DESCRIPTION`, `QUANTITY` and `UNIT_PRICE` are the document's saved business values. Description and price may differ from current Item defaults.
- `SOURCE_LINE_RECORD#` records the exact predecessor line when copied. It is empty for Quote and standalone lines. The downstream line still has its own `RECORD#`.
- Warehouse is obtained from the parent document. Company is stored as `CNY#`; the parent and predecessor foreign keys require the referenced rows to belong to the same company.
- The API's string `line_id` and `source_line_id` serialize these numeric IDs, for example `"1"`. This is a proposed physical mapping; the public field types remain strings.

Line Amount is calculated from Quantity and Unit Price; it is not stored.

## 4. ME_OE_SOURCE_LINKS

Stores the current source selection with its own generated `RECORD#` and owning `CNY#`, following the same primary-key convention as the other Sales tables. Source type and source number are obtained by joining the referenced documents.

```sql
CREATE TABLE ME_OE_SOURCE_LINKS (
    RECORD#                  NUMBER(15) GENERATED BY DEFAULT AS IDENTITY,
    CNY#                     NUMBER(10) NOT NULL,
    SOURCE_DOCUMENT_RECORD#  NUMBER(15) NOT NULL,
    TARGET_DOCUMENT_RECORD#  NUMBER(15) NOT NULL,
    WHENCREATED              TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    WHENMODIFIED             TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT ME_OE_LINK_PK PRIMARY KEY (CNY#, RECORD#),
    CONSTRAINT ME_OE_LINK_COMPANY_FK FOREIGN KEY (CNY#)
        REFERENCES ME_COMPANY (ID),
    CONSTRAINT ME_OE_LINK_SOURCE_UK UNIQUE (CNY#, SOURCE_DOCUMENT_RECORD#),
    CONSTRAINT ME_OE_LINK_TARGET_UK UNIQUE (CNY#, TARGET_DOCUMENT_RECORD#),
    CONSTRAINT ME_OE_LINK_SOURCE_FK FOREIGN KEY (CNY#, SOURCE_DOCUMENT_RECORD#)
        REFERENCES ME_OE_DOCUMENTS (CNY#, RECORD#),
    CONSTRAINT ME_OE_LINK_TARGET_FK FOREIGN KEY (CNY#, TARGET_DOCUMENT_RECORD#)
        REFERENCES ME_OE_DOCUMENTS (CNY#, RECORD#)
);
```

Both document references include `CNY#` and identify `ME_OE_DOCUMENTS(CNY#, RECORD#)`. Join those rows to obtain document types, numbers and Customers.

| Source | Target |
| --- | --- |
| Submitted Quote | Order |
| Submitted Order | Shipper |
| Closed Shipper | Invoice |

A standalone document has no incoming source row. A linked document copies its complete source, with its own header and line identities. The relationship is recorded when the downstream Draft is saved. One source can supply one target, and a target can select one source.

### Invoice source eligibility

An Invoice source lookup returns only Closed Shippers in the authenticated company that the user can read and that are not already used by another Invoice. Submitted and In Progress Shippers are not eligible. Recheck source state and availability when saving the Invoice Draft, changing its source and submitting it. A saved Invoice Draft already reserves its Shipper.

The existing `ME_OE_SOURCE_LINKS` relationship represents this selection; no additional source-state column is stored. A standalone Invoice remains valid with Source blank and follows the same Invoice and payment rules.

Changing or clearing Source updates this relationship with the document save. Deleting an eligible downstream Draft releases it. Returning a target to Draft retains it. Relationship history belongs in shared audit records rather than additional status/history columns here.

The source document number returned by an API is obtained by joining this table to the source header; separate `SOURCE_QUOTE_NUMBER`, `SOURCE_ORDER_NUMBER` and `SOURCE_SHIPPER_NUMBER` columns are unnecessary.

## 5. ME_OE_PAYMENTS

Stores actual received money against an Invoice. Generated `RECORD#` is the internal identifier; `PAYMENT_NUMBER` is its business number. The public Payment contract continues to expose its business number; the internal ID does not introduce a new Payment detail URL.

```sql
CREATE TABLE ME_OE_PAYMENTS (
    RECORD#            NUMBER(15) GENERATED BY DEFAULT AS IDENTITY,
    CNY#               NUMBER(10) NOT NULL,
    PAYMENT_NUMBER     VARCHAR2(20 CHAR) NOT NULL,
    INVOICE_RECORD#    NUMBER(15) NOT NULL,
    PAYMENT_AMOUNT     NUMBER(18,2),
    PAYMENT_DATE       DATE,
    PAYMENT_REFERENCE  VARCHAR2(50 CHAR),
    ACTION_REFERENCE   VARCHAR2(100) NOT NULL,
    WHENCREATED              TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    WHENMODIFIED             TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT ME_OE_PAY_PK PRIMARY KEY (CNY#, RECORD#),
    CONSTRAINT ME_OE_PAY_COMPANY_FK FOREIGN KEY (CNY#)
        REFERENCES ME_COMPANY (ID),
    CONSTRAINT ME_OE_PAY_INVOICE_FK FOREIGN KEY (CNY#, INVOICE_RECORD#)
        REFERENCES ME_OE_DOCUMENTS (CNY#, RECORD#),
    CONSTRAINT ME_OE_PAY_ACTION_FK FOREIGN KEY (CNY#, ACTION_REFERENCE)
        REFERENCES ME_ACTIONS (COMPANY_ID, ACTION_REFERENCE),
    CONSTRAINT ME_OE_PAY_NUMBER_UK UNIQUE (CNY#, PAYMENT_NUMBER),
    CONSTRAINT ME_OE_PAY_ACTION_UK UNIQUE (CNY#, ACTION_REFERENCE)
);

CREATE INDEX ME_OE_PAY_INVOICE_IX
    ON ME_OE_PAYMENTS (CNY#, INVOICE_RECORD#);
```

- `(CNY#, INVOICE_RECORD#)` references the Invoice in `ME_OE_DOCUMENTS(CNY#, RECORD#)`. The service validates type `SALES_INVOICE` and Submitted state when recording payment.
- `PAYMENT_NUMBER` is generated automatically, for example `PAY-001`.
- `PAYMENT_DATE` is the entered business date; it can differ from the server recording timestamp.
- `PAYMENT_REFERENCE` is the entered receipt/transfer reference. It is separate from the API retry reference.
- `(CNY#, ACTION_REFERENCE)` is a declared foreign key to `ME_ACTIONS(COMPANY_ID, ACTION_REFERENCE)`. The company-scoped unique rule on this pair prevents a second Payment for the same recording action.
- Join the shared action using Sales `CNY# = ME_ACTIONS.COMPANY_ID` and the same `ACTION_REFERENCE`; Foundation columns keep their existing names.
- Return `created_by` from `ME_ACTIONS.ACTOR_ID` and `created_at` from Payment `WHENCREATED`, converted to UTC. Retain the shared action records for retry identity and recording-actor history.
- Company is stored directly in `CNY#`. Customer is obtained through the same-company Invoice. Invoice totals and payment status are calculated; the Customer balance is a maintained stored summary. Payment posting protects both the Invoice and Customer balance in one transaction.

Payment history is read through `/sales/invoices/{invoice_number}/payments`, joining the Invoice for its number and the shared action for recording user/time. Sort by Payment `WHENCREATED`, then Payment Number. Payments cannot be edited or deleted in this release.

## Primary keys and references

| Table | Primary key | Foreign key references |
| --- | --- | --- |
| `ME_OE_CUSTOMERS` | `(CNY#, RECORD#)` | `CNY#` → `ME_COMPANY.ID` |
| `ME_OE_DOCUMENTS` | `(CNY#, RECORD#)` | Company; `(CNY#, CUSTOMER_RECORD#)` → Customer `(CNY#, RECORD#)` |
| `ME_OE_DOCUMENT_LINES` | `(CNY#, RECORD#)` | Company; `(CNY#, DOCUMENT_RECORD#)` → Document; optional `(CNY#, SOURCE_LINE_RECORD#)` → predecessor Line |
| `ME_OE_SOURCE_LINKS` | `(CNY#, RECORD#)` | Company; source and target document pairs → Document `(CNY#, RECORD#)` |
| `ME_OE_PAYMENTS` | `(CNY#, RECORD#)` | Company; `(CNY#, INVOICE_RECORD#)` → Document; `(CNY#, ACTION_REFERENCE)` → shared Action |

All Sales references use the child's `CNY#` for the parent company. A foreign key proves row existence and company ownership; services additionally validate document type, workflow state, complete source copying and Invoice due.

Company-scoped unique rules cover Customer Code, document type/number, Payment Number, line position, source/target exclusivity and Payment action reference. These rules can now be enforced directly because each table stores `CNY#`.

## Record timestamps

Every Sales table includes these server-managed fields:

| Field | Type and initial value | Behavior |
| --- | --- | --- |
| `WHENCREATED` | `TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL` | Set on insertion and never changed afterward |
| `WHENMODIFIED` | `TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL` | Set on insertion; the service sets it to `CURRENT_TIMESTAMP` on each accepted update |

The default initializes an inserted row; it does not automatically refresh `WHENMODIFIED` when an UPDATE runs. Customer edits and stored-balance changes, document edits/status transitions, line changes and source-link changes update the affected rows' modification timestamps in the same transaction.

Payments remain immutable in this release, so their modification timestamp stays at its initial value. Deleting a row does not retain its timestamps; deletion and source-release history remain in shared audit records. API callers cannot supply these timestamp values. Payment API `created_at` comes from Payment `WHENCREATED`, normalized to UTC, while `created_by` continues to come from the shared action.

## Foreign key indexes

Every declared foreign key is covered by an index with the foreign-key columns as its leading columns. Three explicit indexes are shown with their table definitions; existing primary-key/unique indexes cover the others without redundant duplicates.

| Table and foreign key | Covering index |
| --- | --- |
| Every Sales table: `CNY#` → Company | Its primary-key index `(CNY#, RECORD#)` |
| Documents: `(CNY#, CUSTOMER_RECORD#)` | Explicit `ME_OE_DOC_CUSTOMER_IX` |
| Lines: `(CNY#, DOCUMENT_RECORD#)` | Unique index `(CNY#, DOCUMENT_RECORD#, LINE_NUMBER)` |
| Lines: `(CNY#, SOURCE_LINE_RECORD#)` | Explicit `ME_OE_LINE_SOURCE_IX` |
| Source Links: `(CNY#, SOURCE_DOCUMENT_RECORD#)` | Source unique index |
| Source Links: `(CNY#, TARGET_DOCUMENT_RECORD#)` | Target unique index |
| Payments: `(CNY#, INVOICE_RECORD#)` | Explicit `ME_OE_PAY_INVOICE_IX` |
| Payments: `(CNY#, ACTION_REFERENCE)` | Payment-action unique index |

## Stored Customer balance

`ME_OE_CUSTOMERS.AMOUNT_CUSTOMER_OWES_US` is a server-maintained summary of all the Customer's Submitted Invoice dues. It is read-only in requests and starts at zero for a new Customer.

| Accepted business transition | Balance effect, exactly once |
| --- | --- |
| Submit an Invoice | Add its total when entering Submitted state |
| Return an eligible unpaid Invoice to Draft | Remove its contribution; any recorded payment blocks return |
| Resubmit that Invoice | Add its contribution again once |
| Record payment | Subtract the actual accepted amount |
| Save Drafts, submit Quote/Order/Shipper, dispatch/close Trip | No balance change |
| Retry an already committed action | Return the saved result; no second balance change |

Lock/protect the Customer row as well as the affected Invoice using an agreed consistent lock order. Persist the Invoice/payment transition, balance update, audit and retry result in the same transaction. Different Invoices for the same Customer must not overwrite each other's balance updates. Roll back all effects if any validation or write fails.

Reconcile the stored balance against the sum of Submitted Invoice totals minus their recorded payments. Validate the 16-whole-digit/2-decimal capacity; do not allow a negative balance, opening balances, credits, refunds or caller-supplied overrides in this release.

## Calculated values and joins

| Value exposed by the API | How it is obtained |
| --- | --- |
| Line Warehouse | Parent document's `WAREHOUSE_ID` |
| Document Customer Code / name | Join document `CUSTOMER_RECORD#` to Customer `RECORD#` |
| Company on documents | Read the document's `CNY#` |
| Company on lines | Read the line's `CNY#`; parent composite key enforces the same company |
| Company / Customer on payments | Read Payment `CNY#`; join Invoice/Customer using same-company composite keys |
| Source number / type | Join Source Link to source document |
| Line Amount | Round `QUANTITY × UNIT_PRICE` half up to 2 decimal places |
| Document Total | Sum the individually rounded line amounts |
| Invoice Total Paid | Sum that Invoice's recorded payments |
| Invoice Amount Due | Document Total minus Total Paid |
| Invoice Payment Status | Empty on Draft; otherwise Unpaid, Partially Paid or Paid based on Total Paid and Amount Due |
| Amount Customer Owes Us | Read stored Customer `AMOUNT_CUSTOMER_OWES_US`, maintained/reconciled from Submitted Invoice dues |
| Payment recording user / timestamp | Shared action's actor; Payment `WHENCREATED` converted to UTC |
| Available actions | Current permissions, document status, source usage and recorded payments |

Derived monetary outputs have 16 whole digits and 2 decimals. Validate calculated capacity before saving/submitting; do not silently round excessive input precision. A zero-total Draft Invoice is allowed, but submission needs a positive total. Draft Invoice dues do not contribute to Customer balance.

## Application behavior

Business workflow rules are enforced by services in addition to the declared primary and foreign keys.

- Compare each record's `CNY#` with the authenticated company on every read/write. Include company in all joins and predicates; composite foreign keys reject cross-company parent/source references.
- Validate required fields, active references, formats, precision, dates and complete lines on Draft save and submission. Inactive Customers remain readable historically and may pay existing Submitted Invoices.
- Only eligible saved Drafts can be edited or deleted. A retained source keeps inherited business fields and copied lines read-only. Deletion is a list action and is blocked by downstream use.
- Save header, lines, source release/claim, audit and retry result together. Validation failure must leave the entire business operation unchanged.

### Return to Draft

| Document | When return from Submitted is allowed |
| --- | --- |
| Quote | No Order uses it, including a Draft Order |
| Order | No Shipper uses it, including a Draft Shipper |
| Shipper | No Logistics Trip assignment and no downstream use, including a Draft Invoice |
| Invoice | No downstream use and no recorded payment |

An In Progress or Closed Shipper can never return to Draft. Recheck Shipper assignment at action time; an earlier list or form response is insufficient. Coordinate with Logistics so Trip assignment and return to Draft cannot both succeed for the same Submitted Shipper.

Returning an eligible unpaid Invoice to Draft removes its contribution from the stored Customer balance in the same transaction and clears its calculated payment status. Resubmitting adds its total once again. Recording a payment leaves Invoice document status Submitted; any payment blocks subsequent return to Draft.

## Logistics integration

Logistics remains the authority for Trip, Shipment, Driver and Trip assignment data. Sales stores its Shipper lifecycle state, while assignment and authoritative Trip state are obtained through the agreed Logistics integration.

### Trip and Shipper association

Prefer reusing a Logistics-owned Trip-Shipper association rather than duplicating Trip, Driver or Shipment columns in `ME_OE_DOCUMENTS`. Confirm the actual association, identifiers and company mapping with Logistics. If no association exists yet, agree its owner and persistence before implementing the integration. No additional Sales column, table or external foreign key is introduced until that decision is settled.

The integration contract must identify the company, linked Shippers, Trip, current assignment, authoritative Trip state and a stable request/event reference. These are integration facts, not a proposed set of new Sales columns.

### Status synchronization

- Apply a relevant Trip dispatch or closure transition to every Shipper linked to that Trip, within the correct company.
- Accept lifecycle updates only from the authorized Logistics integration and preserve source relationships and immutable document business fields.
- Repeated notifications must not repeat business effects. A stale or out-of-order notification must not regress a Closed Shipper.
- Recover from missed or out-of-order notifications by obtaining the authoritative Trip state and reconciling the affected Shippers.
- Agree event delivery, retries and reconciliation with Logistics. Cancellation or reopening behavior needs an explicit agreement; do not infer extra transitions.
- Reuse shared action/audit infrastructure where it supports the agreed integration contract. No Trip, Driver or Shipment master data is duplicated in Sales.

## Concurrency

Locks, stale-edit detection and safe retries address different cases and must work together.

| Operation | Required protection |
| --- | --- |
| Save Customer edits | Update supplied fields atomically; the last committed change to each field wins, with no Customer revision token |
| Save document edits | Reject an outdated revision without overwriting newer saved values or lines |
| Claim, change or release Source | Validate under locks and commit source ownership with the complete document save |
| Return a Shipper to Draft | Coordinate assignment checks and the state change with Logistics |
| Apply Logistics status updates | Resolve duplicate requests and reconcile authoritative state without backward transitions |
| Record payment | Protect the Customer and Invoice, recheck state/due, then save payment, stored balance, audit and retry result together; prevent overpayment and lost balance updates |

### Open revision decision

The requirements still call for revision information and stale-edit rejection. No revision column is added by this update, following the earlier request to remove it. Before implementation, choose a persistent revision mechanism and align it with Swagger's existing `current_version` / `expected_version` fields, or revise those API controls consistently. Locking only while a request runs does not identify a form that was loaded before another user saved changes.

An identical committed retry returns its original result without repeating a payment, source claim or status transition. Reuse `ME_ACTIONS` for request identity and retry results and `ME_AUDIT` for change history, with company ownership enforced.
